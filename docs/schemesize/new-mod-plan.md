# Новый Scheme-Size: рабочая спецификация и архитектура

> **Цель пользователя:** сделать мод, функционально равный Scheme-Size, а затем расширить его и улучшить удобство. Это документирует утверждённое направление; техническая разбивка ниже является рабочим предложением для ИИ-агента.
>
> **Актуальное уточнение:** продукт также включает универсальные инструменты хоста для игровых событий и мини-игр; обязательные ПК-платформы — Windows и Linux, Android исключён; удобный интерфейс в стиле Mindustry — главный критерий. Исследовательский этап ТЗ № 1 завершён. После него полное поручение на реализацию задаёт [ТЗ № 2](TZ_02_full_implementation.md); этот план служит дополнительной архитектурной справкой и не сужает конечный объём работ.

## Цель

Уточнение 02.11.2026: один проект выпускает Scheme-Size Plus и Scheme-Size God Edition. O279 и прогноз клеточных маршрутов — общий слой обеих редакций; панель организатора, ивенты и «Босс-игрок» — God. Подробные критерии и запрет считать совместную установку проверенной заранее — в [ТЗ № 2](TZ_02_full_implementation.md#2-цель-продукта-и-зафиксированные-решения). Различия задаются параметром редакции при регистрации UI/обработчиков, без копирования реализации.

Сделать почти с нуля QoL-мод для Mindustry V8 с полным проверенным набором возможностей Scheme-Size. После закрытия feature-parity добавлять новые функции и улучшения UX отдельными модулями. Не ограничивать проект увеличением размера схем или одной частью старого функционала.

## Рекомендуемый технический вариант

Java/JVM-мод на базе `mindustry.mod.Mod` — наиболее прямой путь для сложного клиентского UI, keybinds и runtime-инструментов. Data patch не умеет добавлять полный набор таких механик; mlog — язык игрока для processor blocks. При появлении серверных функций надо отдельно спроектировать server-side lifecycle/Plugin path.

## Функциональные области

### Обязательный паритет с Scheme-Size

Метаданные upstream подтверждают следующие категории. Сначала агент должен изучить исходники и превратить каждую категорию в список конкретных пользовательских сценариев и критериев готовности:

| Подтверждённая категория | Что требуется выяснить при аудите |
|---|---|
| Flexible control settings | какие игровые настройки/переключатели меняются, как они сохраняются и восстанавливаются |
| Building tools | полный список инструментов, ограничения и режимы применения |
| Shortcuts for schematics | все операции, команды и привязки клавиш со схемами |
| Display of additional info | все HUD/информационные слои и условия отображения |
| Advanced developer console | команды, права, область действия и защитные ограничения |
| Copy Link and Join (CLaJ) | сценарии, сеть, серверная совместимость и зависимости |

Название категории не считается доказательством конкретной реализации. Пока функция не проверена в upstream-коде или интерфейсе, помечай её `needs-audit`, а не `implemented`.

### Расширения после паритета

После обязательной базы агент может добавлять полезные функции, улучшать настройки, навигацию, подсказки, touch-доступность, производительность и совместимость. Идеи из независимого порта (например renderer tools, AI, server sync или более крупные схемы) заноси в отдельный backlog и не смешивай с доказанным upstream-паритетом.

Для каждой новой функции опиши проблему пользователя, способ выключить её, ограничения платформы/сети, влияние на производительность и критерий приёмки.

## Этапы продукта

### P0 — база

- корректное имя, метаданные, version/build checks;
- безопасная загрузка на выбранном V8 build;
- отдельные bootstrap/common/client части;
- простой экран настроек, явные switches для модулей;
- логирование ошибок и понятное поведение при отсутствии необязательной части.

### P1 — схемы

- увеличить или снять согласованный лимит размера;
- проверить полный путь: выделение → копирование → хранение → импорт → экспорт → применение;
- добавить быстрые операции по схемам;
- определить лимит сериализатора/формата отдельно от размеров визуального окна;
- гарантировать, что большие схемы не зависают/не повреждают файл.

### P2 — инструменты строительства и управления

- повтор размещения/поворот/удаление в пределах правил карты;
- отображение дополнительной информации/превью;
- пользовательские keybinds по API V8;
- настройки ввода, которые не требуют мыши (если поддерживаем Android).

### P3 — управление и дополнительная информация

- реализовать все подтверждённые upstream control settings и отображаемые данные;
- независимый toggle для каждого слоя;
- производительная отрисовка с масштабом UI и разрешением;
- отсутствие доступа к клиентскому renderer на dedicated server.

### P4 — консоль и сеть

- отладочная консоль отдельно от массовых игровых действий;
- admin-инструменты с серверной авторизацией;
- CLaJ — обязательная часть паритета; исследовать протокол и поведение upstream. Автоматизация и дополнительные admin-инструменты из независимых портов — отдельный backlog.
- сервер проверяет все входные данные и полномочия, клиент только запрашивает действие.

### P5 — расширения и улучшение UX

- новые функции выпускать после проверенного паритета;
- улучшать навигацию, настройки, подсказки, доступность, надёжность и производительность;
- сохранять базовые рабочие процессы upstream или обеспечивать понятную альтернативу.

## Возможная структура кода

```text
src/main/java/<package>/
├── SchemeSizeMod.java
├── common/         # конфигурация, общий код, совместимость build
├── client/         # UI, HUD, input, визуальные инструменты
├── schematic/      # форматы/операции/сохранение схем
├── building/       # подсказки и строительные помощники
├── admin/          # действия, проверяемые сервером
└── net/            # протокол только при необходимости
src/main/resources/
├── bundles/        # локализация
└── sprites/        # новые ресурсы
```

Это ориентир. Реальную структуру можно упростить после изучения API и проектных требований.

## Границы доступа

| Функция | Где исполнять |
|---|---|
| UI, hotkeys, визуальные подсказки | client |
| локальные настройки/файлы схем | client/local storage |
| обычная постройка | штатные игровые API и rules |
| fill/items/units/teleport/rules в multiplayer | server с правами admin |
| dedicated/headless загрузка | server-safe bootstrap без UI ссылок |

Не доверять только отображению «admin» на клиенте. Решение о действиях, влияющих на серверный мир, принимает сервер.

## Варианты релиза

- Начальный target: Build 160.x, metadata `minGameVersion: 160`.
- Сборка против matching Mindustry/Arc API как compileOnly.
- GitHub Release, например `Scheme Size [v160]`, с JAR.
- В ходе аудита выяснить платформы upstream и стремиться сохранить эту поддержку; проверить JAR на каждой целевой платформе.
- Вести issue/source notes для совместимости; не выпускать «совместимо» только потому, что игра позволяет включить мод.

## Открытые решения, не блокирующие исследование

1. Какие новые функции пользователь добавит сверх обязательного паритета?
2. Какие платформы фактически поддерживал upstream и какие должен поддерживать наш мод?
3. Какой серверный/admin-функционал входит в upstream, а что будет новым расширением?
4. Насколько большой лимит схемы нужен и какие размеры устройств должны его переносить?
5. Какое имя проекта использовать в metadata/UI: `Scheme Size`, `SchemeSize`, `Schema` или другое?

Агент не должен останавливать независимую работу из-за этих вопросов. Сначала изучить upstream и собрать технический список вариантов; пользовательский ввод нужен лишь для решений, которые нельзя вывести из сохранения паритета.

## Минимальный критерий готовности первого кода

Мод собран против выбранного build, проходит feature matrix паритета, загружается в чистой vanilla-сборке, сохраняет upstream-поддержку целевых платформ и окружений, не падает в dedicated/headless пути, которые поддерживал upstream, и не запускает администраторские операции без серверной проверки.
