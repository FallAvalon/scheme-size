Дата проверки: 01.11.2026. Повторный статус: **аудит исходников Scheme-Size 2.7.79 завершён; поведенческие проверки частичные**. Код нового мода не создавался. Оригинальная установка, сохранения и схемы не изменялись. Сопутствующая [матрица функций](01_schemesize_feature_matrix.md) теперь покрывает полный исходный Java-инвентарь релизного тега и отличает проверку кода от запуска.

## Продукт и решения

Пользователю нужен настольный JVM-мод для удобной повседневной работы со схемами и строительством, сохраняющий **полный проверенный функционал оригинального Scheme-Size**, а также панель организатора для управления матчем и событий, в том числе игры «босс-игрок». Организатор устанавливает мод на компьютере встроенного хоста; остальные участники должны подключаться обычной игрой. Удобство и привычный стиль Mindustry имеют первостепенное значение; Windows и Linux обязательны, Android не требуется.

Подтверждённые желания: инструменты схем и строительства, гибкие настройки и горячие клавиши, информация, правка подходящих правил в матче, управление игроками и командами, юнитами, ресурсами и ареной, события и пресеты. Окончательные операции, права и условия сценария надо определить после аудита. «Босс-юнит», волны/выживание, командная битва и дуэль — **предложения**, а не утверждённые режимы.

### Новые сведения из аудита 2.7.79

- Тег сборки фиксирует `mindustryVersion = v146`, `minGameVersion: 146`, `sourceCompatibility = 20`, `targetCompatibility = 8` через Jabel. Поэтому `minGameVersion` не описывает проверенную совместимость с V8. При этом отдельный запуск установленного релизного архива в копии API 160.7 прошёл стадию загрузки мода.
- `Main.init()` не только добавляет инструменты: мод заменяет обработчики ввода, библиотеку схем и список игроков, меняет `GlyphLayout`, устанавливает глобальные build-типы для `distributor` и всех `LogicDisplay`, добавляет UI/рендереры и исполняет собственный `scripts/main.js` в контексте консоли игры. Это повышает риск несовместимости с другими модами; описанное upstream «Vanilla Only» — рекомендация автора, не проверенная гарантия.
- В админ-панели три разных пути: `Internal` локально меняет игровые объекты; `SlashJs` отправляет команды `/js`; `Darkdustry` отправляет команды/пакеты, ожидающие серверную поддержку Darkdustry. У них различаются права и сетевой путь. В частности, `Internal` при сетевом клиенте по умолчанию блокируется, а `adminsalways` снимает блок без проверки `player.admin`; это не безопасная серверная авторизация. `SlashJs` и `Darkdustry` — отдельные механизмы, не считать их доказательством поддержки vanilla dedicated.
- Исходный набор hotkeys теперь сопоставлен не только с enum, но и с обработчиком. Базовые бинды: F12 — настройки админ-инструментов; Y — renderer; G — быстрое меню схем; F7 — предметы ядра; I — выбор AI; F2/F3/F4 — юнит/эффект/предмет; `;` — команда игрока; `'` — ядро; Left Alt — модификатор. Alt + F2 создаёт юнитов, Alt + I сбрасывает AI, а прочие сочетания см. в матрице. Локальные клавиши не переназначают автоматически управление vanilla-клиентов.
- Для пользовательского сценария «босс-игрок» оригинал не содержит готового режима/счёта раунда. Его админ-функции дают отдельные строительные действия, смену команды, юнитов и эффекты; условия победы, респавн, отключение игрока и восстановление мира предстоит спроектировать в новом моде.

## Архитектура и граница доверия

**Предложение:** JVM-мод `mindustry.mod.Mod`, с отдельными модулями UI/локального ввода, общих операций схем и авторитетной логики события. `Mod.init()` и серверные/клиентские команды указаны в [Mod.java v160.7](https://github.com/Anuken/Mindustry/blob/v160.7/core/src/mindustry/mod/Mod.java#L8). Встроенный хост содержит и клиентскую, и серверную стороны; локальная UI-команда должна попасть в авторитетную часть в том же процессе. Одиночная игра — отдельный локальный путь без удалённых клиентов. На dedicated отдельная установка серверного модуля **на сам сервер** обязательна для новых серверных функций; локальный мод администратора не получает полномочий изменять чужой ванильный сервер. Удалённая панель для dedicated — возможное расширение, не текущая обязательная цель.

Для подключений Build 160.7 `Mods.getModStrings()` исключает `hidden`-моды, а `NetServer` сравнивает списки и отклоняет несовпадения: [Mods.java:967](https://github.com/Anuken/Mindustry/blob/v160.7/core/src/mindustry/mod/Mods.java#L967), [NetServer.java:210](https://github.com/Anuken/Mindustry/blob/v160.7/core/src/mindustry/core/NetServer.java#L210). **Подтверждено кодом/API:** это даёт основание проектировать скрытый host-only мод без нового синхронизируемого контента. В том же build загрузчик пропускает `loadContent()` скрытого Java-мода ([Mods.java:3542](https://github.com/Anuken/Mindustry/blob/v160.7/core/src/mindustry/mod/Mods.java#L3542)); будущая реализация должна обходиться без собственных типов контента. **Вероятно, требуется прототип:** настоящий вход ванильного клиента и каждая операция; `hidden` сам по себе не делает пользовательские пакеты, типы юнитов, блоки или виджеты понятными ванильной игре. Новые визуальные UI и хоткеи доступны только на машине с модом.

Не передавать клиенту произвольные исполняемые строки. При наличии удалённых административных запросов сервер проверяет идентичность, полномочия, состояние матча, допустимые значения, ограничения размера и частоты, затем применяет и синхронизирует действие. Клиентская блокировка кнопки не является проверкой прав. Headless-ветка не должна вызывать `ui`, `control`, `netClient` или привязанные к графике объекты. Для опасных изменений нужны видимый контекст, ограничение объёма и подтверждение внутри будущего UI.

## Операции организатора: где исполняются и как видны

В таблице «подтверждено кодом/API» относится к существованию указанного механизма, **не** к фактическому тесту сети. В каждом случае точка изменения — локальная игра либо серверная часть встроенного хоста/установленного dedicated. Для запроса с удалённого администратора необходима повторная серверная проверка; обычный участник не получает новых прав.

Безопаснее отдельно проектировать событие раунда и протестировать перезапуск. |
| Произвольная операция с ПК администратора на чужом vanilla dedicated | Только штатные запросы и права, которые уже понимает сервер. | **Не поддерживается/требует серверной части** для новой авторитетной логики и протокола. Установка мода только у клиента недостаточна. |

Порт использует `ServerSide` с проверкой `player.admin` и отдельными пакетами, а внутренний путь вызывает `Call.setRules`: [ServerSide](https://github.com/ItsXeroc/Scheme-Size/blob/9327f72eed19ef957bb9b3e74ea03120cb7dd8e1/src/java/scheme/ServerSide.java#L182), [Internal](https://github.com/ItsXeroc/Scheme-Size/blob/9327f72eed19ef957bb9b3e74ea03120cb7dd8e1/src/java/scheme/tools/admins/Internal.java#L32). Это конкретный пример архитектуры порта, а не независимое подтверждение её безопасности или совместимости с 160.7.

## «Босс-игрок»: рабочая гипотеза

1. Подготовка: хост выбирает подключённого игрока и отдельную ванильную команду босса; участникам назначает другую, выбирает карту и поддерживаемые правила. Сервер сохраняет исходные настройки и контролирует целостность состава.
2. Старт: сервер устанавливает команды, согласованный тип юнита и множители команды, сообщает правила через штатное объявление. При смене команды проверить, какой юнит фактически контролируется и как работают возрождение и ядро.
3. Ход: сервер отслеживает смерть/потерю управления/отключение игрока босса, состояние претендентов и таймер. Событие завершения должно срабатывать один раз и не конфликтовать со штатной победой по ядрам. Правила для ничьей, выхода, повторного входа и респавна пока не утверждены.
4. Завершение: объявить победителя штатным сообщением, зафиксировать счёт на стороне организатора, восстановить правила и позиции согласно выбранной политике и подготовить следующий раунд. Перезагрузка карты или восстановление снапшота требуют отдельного решения и тестирования.

Это проект, **не подтверждённая реализация**. Для полноценной индивидуальной механики босса поверх ванильного протокола могут понадобиться ограничения или серверная имитация; решение зависит от требуемых способностей.

## UI, управление и локальные данные

Предложение для обсуждения: небольшая кнопка HUD и переназначаемая клавиша открывают сворачиваемую панель, не закрывающую центр поля. Основа — штатные `BaseDialog`, `Table`, `Styles`, `Icon`, `Pal`, локализация, масштаб и настройки самой игры. Штатное расширение настроек: [SettingsMenuDialog:322](https://github.com/Anuken/Mindustry/blob/v160.7/core/src/mindustry/ui/dialogs/SettingsMenuDialog.java#L322). В V8 существующие клавиши регистрируются через [Binding/KeyBind.add](https://github.com/Anuken/Mindustry/blob/v160.7/core/src/mindustry/input/Binding.java#L8); учёт контекста и предупреждение конфликтов надо спроектировать и проверить, а не считать готовыми из одного вызова. Некоторые функции уже присутствуют в игре: команды, выбор/поворот схем, разрешения, правила, сообщения, настройки. Новый UI должен интегрировать их, не подменяя незаметно стандартный ввод.

```text
HUD: [инструменты]  [статус: одиночная / хост / клиент]
  Схемы | Строительство | Информация | События | Администрирование | Настройки
  Схемы: выбор / метки / операции / ограничения
  События: подготовка -> запуск -> раунд -> завершение -> следующий раунд
    Босс: игрок, команда, параметры, состав, таймер, статус, объявление
  Администрирование: игроки / команды / юниты / предметы / арена / правила
  Настройки: включение модулей, подсказки, клавиши и конфликты,
             расположение/скрытие, масштаб игры, профили, пресеты, сброс
```

Это не окончательный макет. У каждой недоступной команды — причина: одиночная игра, хост или необходимость серверной части; отдельные локальные функции доступны обычному пользователю с модом. Команды ведущего должны иметь фильтрацию цели, единицы измерения, предпросмотр и обратную связь. Профили, хранение пресетов через `Mod.getConfigFolder()`/`Core.settings`, версионирование и экспорт — предложения; нельзя считать реализованными. Перетаскивание и масштаб проверить на разных разрешениях и с UI scale.

## Windows и Linux

Игра и порт используют JVM/desktop-путь; исходники релиза собирают Java 17 ([build.gradle:197](https://github.com/Anuken/Mindustry/blob/v160.7/build.gradle#L197)). Рекомендуется JDK 17 для сборки и фиксированные зависимости Mindustry/Arc точного build, Gradle Wrapper и отдельный desktop JAR; конкретные команды `./gradlew …` и `gradlew.bat …` станут проверяемыми после создания сборочного проекта. Системная Java 8 недостаточна для обычной Java-17 сборки без дополнительных инструментов; встроенная JRE 25 не является установленным JDK. На Windows проверен только запуск изолированной копии и обнаружение O279 загрузчиком. Linux не запускался: в среде нет Linux/WSL-дистрибутива, Docker или Podman. Для обеих платформ остаются проверки функций, UI, клавиш, путей и сборки; macOS не заявляется.

## Первый проверочный срез и матрица испытаний

Рекомендуемый будущий срез после ТЗ № 2: отдельный тестовый мир, панель хоста, одно ограниченное изменение количества предмета в ядре своей команды с демонстрацией на ванильном клиенте, затем проверка отключения и повторного входа. До любых испытаний использовать отдельный профиль/каталог и копии тестовых данных; не трогать существующие сохранения. Записать номера build, тип запуска, ID артефакта, исходное и итоговое значение на обеих сторонах, логи и результат.

| Среда/сценарий | Критерий приёмки | Сейчас |
|---|---|---|
| Windows solo | загрузка, UI и изменение предмета видимы, выход/повторное открытие тестового мира | только запуск приложения и обнаружение мода загрузчиком; UI, мир и действия не проходились |
| Windows встроенный хост + vanilla 160.7 | вход без мода, значение ядра совпадает на обеих сторонах, поздний вход и переподключение | не выполнялся |

## Риски и открытые решения

| Вопрос | Рекомендация и риск |

Все 52 Java-файла тега инвентаризированы, ключевые классы прочитаны; локальный архив сверен с тегом по метаданным и ресурсам.
